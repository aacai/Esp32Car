## 1. 看实时日志：三条路

### 路线 A：串口（最全，能看到崩溃现场）★推荐

```bash
python3 tools/serial_log.py
```

就这一条命令，日志会实时刷出来，`Ctrl+C` 退出。

**为什么必须用这个脚本，不能用 `idf.py monitor`？**
这块板是 ESP32-C3 **原生 USB（USB_SERIAL_JTAG）**，DTR/RTS 的实际极性：
**DTR 置高会把 EN 拉低、把芯片按在复位里（一个字节都读不到）；DTR 置低才是运行态。** 普通工具 / `idf.py monitor` 默认电平不对，要么按在复位里、要么带进下载模式 —— 表现就是"插上了但一行日志都没有"。
本脚本把 DTR/RTS 固定为低电平（这块板 DTR 置高反而会把芯片按在复位里），所以能正常读日志。

> 注：本板在 CDC 口被打开的瞬间，硬件会产生**一次**复位脉冲（日志里可见 `rst:0x15 USB_UART_CHIP_RESET`），这是正常的 —— 复位后日志照常输出，不影响使用。想看完整开机横幅，就在抓日志前先手动给板子断电重插一次。

常用参数：

| 命令 | 作用 |
|------|------|
| `python3 tools/serial_log.py` | 实时跟随 |
| `python3 tools/serial_log.py --analyze` | **抓 10 秒并自动诊断崩溃/重启** ← 出问题先跑这个 |
| `python3 tools/serial_log.py -t 20` | 只抓 20 秒 |
| `python3 tools/serial_log.py -o log.txt` | 同时存文件 |

`--analyze` 的输出长这样：

```
============================================================
诊断结果
============================================================
  启动次数 : 1
  abort 次数: 0
  ✅ 运行稳定，无异常重启
  [复位原因] rst:0x15 (USB_UART_CHIP_RESET)
============================================================
```

如果**启动次数 > 2**，说明板子在反复重启，脚本会直接把出错文件、行号、函数、表达式打出来。

> 提示：如果报 `Resource busy`，说明有别的程序占着串口，先关掉 `idf.py monitor` 或其它串口工具。

### 路线 B：网页（不用插线，手机也能看）

板子现在会把所有日志存在内存里（最近 96 行），通过网页实时显示。

1. 浏览器打开小车网页
2. 往下拉，找到 **「🖥 固件实时日志」** 面板

面板功能：

| 按钮 | 说明 |
|------|------|
| ⏸ 暂停 | 冻结画面，方便看某一段 |
| 🧹 清屏 | 清空显示 |
| ⬇ 自动滚动 | 关掉后画面不会被新日志顶走 |

日志按等级配色：<span>**E**=红（错误）</span>、**W**=黄（警告）、**I**=蓝（信息）。
板子重启后面板会自动检测并提示「检测到板子重启」。

> **注意**：崩溃瞬间的 panic 信息（`Guru Meditation`、backtrace）走的是底层直写串口，
> **不经过内存缓冲**，网页上看不到。查崩溃必须用路线 A。

## 2. 怎么确认蓝牙到底正不正常

### ⚠️ 先记住这一条

**ESP32-C3 是纯 BLE 设备。手机和电脑的「设置 → 蓝牙」页面不会列出未配对的 BLE 外设。**

所以「设置里看不到」**根本不能说明固件有问题** —— 那是系统行为。

### 正确的查看方式

**手机上**：装 **nRF Connect**（安卓/iOS 都有）或 **LightBlue**（iOS），打开就能扫到 `EspCar_XXXXXX`。

**电脑上**（不用手机，最快）：

```bash
python3 tools/ble_scan.py
```

输出：

```
[14:14:05] 扫描完成，共发现 9 个 BLE 设备

  ✅ 找到小车（1 个）：
     RSSI  -46 dBm  EspCar_FE1036
```

这就是**确定性结论**：扫到了 = 固件蓝牙完全正常。

如果没扫到，脚本会告诉你下一步查什么。常用参数：

| 命令 | 作用 |
|------|------|
| `python3 tools/ble_scan.py` | 扫 10 秒 |
| `python3 tools/ble_scan.py -a` | 顺便列出周围所有 BLE 设备 |
| `python3 tools/ble_scan.py -w` | 持续监视，掉线立刻能发现 |

### 网页上也能看

「实时状态」面板里有两栏：

- **BLE 广播**：`广播中` = 正常 / `失败(码)` = 启动出错 / `未启动` = 协议栈没跑起来
- **蓝牙状态**：有没有设备连上来

## 2.1 从电脑真正连上去、发指令（端到端验证，最硬的证据）

光"扫到"还不够，下面这条命令会让你的 Mac **真正发起 GATT 连接**、枚举服务、读状态、发一条控制指令：

```bash
python3 tools/ble_connect_proof.py            # 连接 + 读状态 + 发一次 'F'(前进)
python3 tools/ble_connect_proof.py --cmd S     # 连接并发指定指令 (F/B/L/R/S/0-9)
```

一次成功运行的真实输出（节选）：

```
✅ 找到 EspCar_FE1036 @ 6D61A7AA-...
🔗 已连接: True
  服务 0000abcd-...  <<< 小车
    特征 00001234-...  [write]        # 指令通道 F/B/L/R/S
    特征 00001235-...  [read,notify]  # 状态通道
📤 已发送指令: 'F'
📥 状态返回:
   {"ip":"192.168.50.100","uptime":13,...,"last_cmd":"F","action":"前进","cmd_count":1,"ble":1,...}
🔌 已断开
```

同时固件侧（串口）会打印：

```
I (11664) ble_car: BLE 已连接
I (12764) ble_car: BLE 指令: F
I (13964) ble_car: BLE 已断开，重新广播
```

**连上、收到指令、状态变成"前进"、干净断开重广播**，这就是你的苹果电脑确实连上了这个蓝牙的铁证。
（系统「设置 → 蓝牙」依然不显示它，那只是 BLE 外设的系统行为，不是没连上。）

## 3. 怎么连上小车网页

### 方式一：小车自带热点（最稳，任何时候都能用）

1. 手机/电脑 WiFi 列表里找 **`EspCar_XXXXXX`**
2. 密码 **`12345678`**
3. 浏览器打开 **http://192.168.4.1**

### 方式二：和小车连同一个路由器（实测 Mac 可直接用）

车连上 `ImmortalWrt-2.4G` 后 IP 为 `192.168.50.100`，与 Mac 同处 `192.168.50.x` 网段。
浏览器直接打开 **http://192.168.50.100/** 即可遥控，无需切到小车热点。

想先确认通不通，命令行验一下（不依赖串口、不复位车）：

```bash
curl -s --max-time 6 http://192.168.50.100/status | python3 -c \
  "import sys,json;d=json.load(sys.stdin);print('ip',d.get('ip'),'wifi_state',d.get('wifi_state'))"
# 期望输出: ip 192.168.50.100 wifi_state connected
```

> **说明**：实测 Mac 可直接访问同网段小车，客户端隔离未阻断 Mac→小车。
> 若你的某台电脑打不开，检查路由器是否对该设备开了 **AP isolation**，或改用**方式一**（小车热点）。
> 状态 JSON 里 IP 字段名是 `ip`（不是 `wifi_ip`）。

## 8. Mac 端一条龙联调（不用手机，WiFi + BLE 实测）

想快速确认「车到底连没连上 WiFi、蓝牙能不能收发消息」，在 Mac 上两条命令就够，
全程**不依赖串口**（避免打开串口误复位车）。

### 7.1 WiFi 网页链路实测

车已连上 `ImmortalWrt-2.4G`，IP 固定 `192.168.50.100`，与 Mac 同网段。直接验：

```bash
# 主页是否返回 HTML（期望看到 <!DOCTYPE html> ... 小车遥控）
curl -s --max-time 6 http://192.168.50.100/ | head -c 120

# 状态接口：确认 wifi_state 与真实 IP（期望 ip 192.168.50.100, wifi_state connected）
curl -s --max-time 6 http://192.168.50.100/status | python3 -c \
  "import sys,json;d=json.load(sys.stdin);print('ip',d.get('ip'),'wifi_state',d.get('wifi_state'),'last_cmd',d.get('last_cmd'))"
```

浏览器直接打开 `http://192.168.50.100/` 即可图形化遥控。

> 注意：状态 JSON 里 IP 字段名是 `ip`（不是 `wifi_ip`），脚本取字段名要对。

### 7.2 BLE 收发链路实测

两种方式任选其一：

**方式 A：图形化（日常推荐）**

```bash
python3 ble_remote_gui.py
```

界面里：扫描 → 选 `EspCar_XXXXXX` → 连接 → 点 `F 前进` / `S 停止`（或键盘 ↑↓←→ + 空格）。
右侧状态面板实时显示车回传的 JSON（`last_cmd` / `action` / `cmd_count` 递增），
这就是「车真的收到并回消息」的证据。`tkinter` 为 Mac 自带，无需额外安装。

**方式 B：命令行（最硬证据，详见第 2.1 节）**

```bash
python3 tools/ble_connect_proof.py        # 连车 + 发 F + 收状态回执
```

实测一次 BLE 收发长这样（Mac 主动连 + 发 F + 订阅状态通知回执）：

```
[BLE] connected: True
[BLE] 发送 F (前进) ...
  [BLE 收到车回执] {"ip":"192.168.50.100","last_cmd":"F","action":"前进","cmd_count":1,"ble":1,...}
```

连上、发出指令、车回 JSON、干净断开 —— 双向收发都通。

### 7.3 两条链路同时在线

车是 **APSTA 双模 + BLE 同时在线**：WiFi 网页遥控 与 BLE 遥控 可并存，互不干扰。
测 BLE 时不需要断开 WiFi；测 WiFi 时也不需要断开 BLE。

## 6. 在线升级固件（OTA，不用插线）

固件支持 **OTA 在线升级**：通过网页或 Python 脚本把 `.bin` 推给小车，它自动写入**另一个 OTA 分区**、切换启动分区、重启生效。分区表是双 OTA（ota_0 / ota_1 / otadata），每次升级在两块之间来回切，**不会覆盖正在跑的固件，升级失败也能回退**。

### 6.1 方式一：网页上传（最省事）

1. 打开小车网页（热点 `http://192.168.4.1` 或同网段 `http://192.168.50.100/`）
2. 拉到底部 **「在线升级固件」** 卡片
3. 点「选择固件」选 `.bin`（注意：是 `build/esp32c3_iot.bin`，**不是** `build/CarProject.bin` 也不是 bootloader）
4. 弹窗二次确认 → 点「升级」，进度条走完
5. 小车写入另一分区后会**自动重启**，重启完网页自动刷新恢复

> 上传期间小车会闪灯属正常。升级中**不要断电、不要刷新页面**。

### 6.2 方式二：Python 脚本（命令行 / 可脚本化）

```bash
# 自动探测小车（先试热点 192.168.4.1，再扫网段），直接传固件
python3 tools/ota_upload.py build/esp32c3_iot.bin

# 已知地址时显式指定（省去探测，更快）
python3 tools/ota_upload.py -H 192.168.4.1    build/esp32c3_iot.bin
python3 tools/ota_upload.py -H 192.168.50.100 build/esp32c3_iot.bin

# 非 80 端口 / 关掉进度条
python3 tools/ota_upload.py -H 192.168.4.1 -p 8080 build/esp32c3_iot.bin
python3 tools/ota_upload.py --no-progress build/esp32c3_iot.bin
```

成功输出示例：

```
目标：http://192.168.50.100:80/update
固件：esp32c3_iot.bin  (1.10 MiB)
开始上传（上传期间小车会闪灯属正常）…

上传进度: 100%|████████| 1.10M/1.10M [00:03<00:00, 350KiB/s]
✅ 升级请求已接受：{"ok":1,"msg":"upgrade-ok-reboot"}
小车正在写入新分区并重启，稍候刷新网页即可。
```

设备串口会打印 `OTA 升级完成，目标分区 ota_1，准备重启`；重启后 bootloader 日志里 `Loaded app from partition at offset 0x1a0000` 即代表已从 ota_1 启动（ota_0 偏移是 `0x10000`）。

### 6.3 接上次 OTA 失败 / 想确认升级结果

- 升级后点一下网页「实时状态」看 `uptime` 是否归零（重启了=生效了）。
- 想 100% 确认从哪块分区启动，串口抓启动横幅：搜 `Loaded app from partition at offset`
  - `0x10000`  → ota_0
  - `0x1a0000` → ota_1
- 升级中途断了？**没关系**，当前跑的固件没被碰过，重启还是老版本，重新传一次即可。

### 6.4 注意事项

- **只传 `build/esp32c3_iot.bin`**（应用固件），不是 `bootloader` / `partition-table` / 合并 bin。
- 首次烧录换成分区表时，必须**整片重烧**（见第 7 节），否则旧分区表没有 ota 槽位、OTA 会报“超出分区”。
- 若小车连着外部路由器，`192.168.50.100` 与 Mac 同网段可直接推；连不上再用热点 `192.168.4.1`。

## 7. 编译和烧录

> **推荐用封装脚本**（已修好本机 `python` 被 ServBay 别名遮蔽导致 `idf.py build` 报 `Cannot import module esp_idf_monitor` 退出的坑）：

```bash
bash tools/idf.sh build                       # 编译
bash tools/idf.sh -p /dev/cu.usbmodem1101 flash   # 烧录（含新分区表）
```

脚本内部已强制把 idf 自带 venv python 放到 PATH 最前，不用再手设环境变量。

如果**不用脚本、想手动来**，必须先设对 PATH（否则 ServBay 的 `python` 会抢前面、缺 idf 依赖而失败）：

```bash
export IDF_PATH=$HOME/esp/esp-idf   # 改成你本机的 ESP-IDF 安装路径
. $IDF_PATH/export.sh               # export.sh 会自动把 idf 的 python venv 加入 PATH

idf.py build
```

烧录（手动方式，`idf.py flash` 在这台机器上有 PATH 问题，直接用 esptool）：

```bash
cd build
python -m esptool --chip esp32c3 -p /dev/cu.usbmodem1101 -b 460800 \
  --before default_reset --after hard_reset --no-stub write_flash "@flash_args"
```

> 烧录前记得先 `Ctrl+C` 停掉 `serial_log.py`，否则串口被占用。
> **换了双 OTA 分区表后，首次必须整片重烧**（上面的 `flash` 命令已包含分区表）才能拿到 ota 槽位，之后才能用第 6 节 OTA 升级。

## 附：这次踩过的坑（避免重蹈覆辙）

| 现象 | 真实原因 |
|------|----------|
| 手机搜不到蓝牙 | 板子在 **10 秒重启 34 次**，蓝牙压根没机会启动 |
| 为什么会重启 | `esp_wifi_set_config(WIFI_IF_AP,…)` 写在了 `esp_wifi_set_mode(APSTA)` **前面**，返回 `0x3005`，被 `ESP_ERROR_CHECK` 直接 `abort()` |
| 为什么拖了这么久 | 一直以为"Mac 上看不到串口日志"，实际上**禁用 DTR/RTS 就能看** |
| 就算不重启也起不来 | `ble_car_init()` 手动调了 `esp_bt_controller_init()`，而 `nimble_port_init()` 内部还会再调一次 → 返回 `0x103` → BLE 主机不启动 |
| 现在怎么防 | WiFi 任务改用 `WIFI_TRY()`：出错只结束 WiFi 任务，**绝不 abort 整机**，蓝牙和网页不再被连累 |
| WiFi 连上了却马上又重启 | `wifi_init_sta` 是 FreeRTOS 任务，等连接结果后直接 `return` 了 → FreeRTOS 报 `wifi_init should not return, Aborting now!` → `RTC_SW_CPU_RST` 死循环。修法：任务结尾 `vTaskDelete(NULL)` 主动退场，别 return |
| 串口脚本改成 DTR 高反而不出日志 | 这块 ESP32-C3 原生 USB 极性相反：**DTR 高 = 把 EN 拉低按在复位里（0 字节）**，DTR 低才是运行态。脚本已固定为低电平 |
| 安卓连 BLE 弹“PIN/密钥不对 / 拒绝配对” | **根因：MIUI/安卓在蓝牙设置里点设备会强制 `createBond` 发起配对/绑定，车端必须能接。** 三种情况：(1) 开放 GATT（没开 SMP）→ 车直接拒绝 → “已拒绝配对”；(2) 开了 SMP 但用**安全连接 SC**（`sm_sc=1`）→ 安卓连上、开始绑定，但加密阶段被拒（`0x0D` Connection Rejected Due To Security Reasons），绑定 30s 超时 → “PIN/密钥不对”；(3) ✅ SMP 用 **Legacy Just Works**（`sm_sc=0`、`sm_io_cap=NO_INPUT_OUTPUT`、`sm_mitm=0`、`sm_bonding=1`、`sm_our/their_key_dist=ENC[+ID]`、`ble_hs_cfg.store_status_cb=ble_store_util_status_rr` + `ble_store_config_init()`）→ 安卓点一下“配对”即绑定成功（约 3 秒，无 PIN、不弹窗），LTK 持久化到 NVS。车端 `on_sync` 用 **public 地址**（`BLE_OWN_ADDR_PUBLIC`），与安卓记录的 MAC 一致。GATT 特征不要求加密，所以纯连接（不配对）也能收发 F/B/L/R/S —— 两种用法都支持。**已用 ADB + 安卓真机自测通过**：`BLE-CONNECTED … Success` → `BOND_STATE_BONDING` → `BOND_STATE_BONDED`，车端串口 `加密/配对状态变化: status=0`。sdkconfig 需 `CONFIG_BT_NIMBLE_SECURITY_ENABLE=y` + `SM_LEGACY=y` + `LL_CFG_FEAT_LE_ENCRYPTION=y` + `NVS_PERSIST=y`（`SM_SC` 保留开启只是能力，代码用 `sm_sc=0` 走 Legacy）。 |
| 用 ADB 自动化测试安卓配对时“找不到设备” | 安卓蓝牙设置页**已在前台运行时**再 `am start` 不会重启 Activity、也就不触发扫描 → 一直扫不到车。必须每轮先 `am force-stop com.android.settings`（MIUI 也可能是 `com.miui.settings`）再 `am start -S -a android.settings.BLUETOOTH_SETTINGS`，强制冷启才会在扫描窗口里列出 `EspCar_XXXXXX`。配对弹窗只点“配对/确定/是”等短标签，别点“连接设置”之类的菜单项（会误触通知/设置） |
| WiFi“连不上去” | **先别急着改代码——当前固件其实能连，已自测通过。** 板子用官方 station 示例与小车固件都连上了 `ImmortalWrt-2.4G`（`WPA2-PSK, channel 5`），拿到 `192.168.50.100`（信号约 -30dBm）。小车是 APSTA 双模：STA 连外部 WiFi + 自有 AP `EspCar_XXXXXX`（DHCP `192.168.4.1`）+ 网页服务（`/`、`/api`、`/status`、`/mylog`）同时工作。若你“看着像没连上”，多半是：(1) **开机不在路由器覆盖范围内**——首轮连不上后要等 `wifi_scan_reconnect_task` 每 30s 才重试，走近才连；(2) **手机连的是车自己的 `EspCar_XXXXXX` AP**——APSTA 下 STA 一连上外部 WiFi，ESP-IDF 会把 AP 信道从 1 自动挪到 STA 的信道（日志 `ap channel adjust o:1,1 n:5,1`），部分手机还停在旧信道会一时找不到 AP，但网页控制本身可用。排查：串口看 `WiFi 已连接，IP=…`；小车断线现在会打印 `WiFi 断开! reason=N`（对照 ESP-IDF reason code 表：2=认证失败/密码错、3=无此 AP、4=密钥交换失败等）。校验用的官方示例在 `../wifi_example/`。 |
